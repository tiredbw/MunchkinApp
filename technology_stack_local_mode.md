# Технический стек: локальное кроссплатформенное приложение-помощник для настольной игры

## 1. Цель первой версии

Первая версия работает полностью в локальной сети без облачного сервера. Один телефон, планшет или компьютер создаёт комнату и становится **хостом**. Остальные устройства подключаются к нему по Wi‑Fi и работают как клиенты.

```text
Устройство ведущего
Flutter-приложение
HttpServer + WebSocket-сервер
Главное состояние партии
        │
        ├── Android/iPhone игрока 2
        ├── Android/iPhone игрока 3
        ├── iPad
        └── Mac
```

Хост — единственный источник истины (**authoritative host**): он проверяет команды, изменяет состояние, увеличивает его ревизию и рассылает события или полный снимок всем клиентам. Клиенты не меняют общее состояние самостоятельно.

## 3. Архитектура соединения

Игровая логика не должна зависеть от WebSocket. Для этого используется абстракция:

```dart
abstract interface class GameConnection {
  Stream<GameEvent> get events;
  ConnectionStatus get status;

  Future<void> connect(ConnectionConfig config);
  Future<void> send(GameCommand command);
  Future<void> disconnect();
}
```

Реализации:

- `LocalHostConnection` — запускает локальный сервер и одновременно подключает интерфейс хоста к игровой сессии;
- `LocalClientConnection` — подключается к хосту по WebSocket;
- `SupabaseGameConnection` — будущая реализация облачного режима без переписывания экранов и доменной логики.

Репозитории и контроллеры зависят только от `GameConnection`. Riverpod предоставляет выбранную реализацию через provider. Это позволит позже добавить Supabase (Auth, Realtime и Postgres), сохранив команды, события и модели домена.

## 4. Локальный сервер и подключение

Хост запускает `HttpServer.bind()` на доступном сетевом интерфейсе и выбранном порту. WebSocket-подключение создаётся через upgrade HTTP-запроса. Адрес комнаты имеет вид:

```text
ws://192.168.1.25:8787/ws?roomId=<id>&token=<token>
```

QR-код содержит версию ссылки, IP, порт, `roomId` и случайный `roomToken`. Пользователь сканирует его, вводит отображаемое имя и отправляет команду подключения. Токен лучше не показывать открытым текстом; хранить его следует в `flutter_secure_storage`.

На первой версии автоматический поиск не обязателен: QR надёжнее и проще. В будущем хост сможет публиковать сервис через **mDNS/Bonjour**, а клиенты — показывать комнаты поблизости. QR-код останется резервным способом.

При потере связи клиент повторно подключается с экспоненциальной задержкой и передаёт последнюю известную ревизию. Хост отвечает недостающими событиями, если они ещё хранятся, либо полным снимком `GameState`.

## 5. JSON-протокол

Каждое сообщение имеет конверт:

```json
{
  "protocolVersion": 1,
  "messageId": "uuid",
  "type": "command.updatePlayer",
  "roomId": "uuid",
  "senderId": "uuid",
  "expectedRevision": 12,
  "sentAt": "2026-08-01T12:00:00Z",
  "payload": {}
}
```

`protocolVersion` обеспечивает совместимость версий приложения, `messageId` — дедупликацию, а `expectedRevision` — защиту от применения команды к устаревшему состоянию. Даты передаются в UTC в ISO 8601. Денежные значения и игровые параметры, где возможно, передаются целыми числами.

### Команды клиента

- `joinRoom` — войти в комнату по имени и токену;
- `leaveRoom` — покинуть комнату;
- `updatePlayer` — изменить разрешённые поля игрока;
- `startGame` / `endGame` — начать или завершить игру (только хост);
- `startTurn` / `endTurn` — управление ходом;
- `startBattle`, `updateBattle`, `resolveBattle` — управление боем;
- `rollDice` — запросить бросок кубика;
- `requestSnapshot` — запросить актуальное состояние;
- `ping` — проверка соединения.

Команда описывает намерение, но не гарантирует изменение. Хост проверяет токен, роль, фазу игры, диапазоны значений, `expectedRevision` и права отправителя.

### События хоста

- `playerJoined`, `playerLeft`, `playerUpdated`;
- `gameStarted`, `gameEnded`;
- `turnStarted`, `turnEnded`;
- `battleStarted`, `battleUpdated`, `battleResolved`;
- `diceRolled`;
- `stateSnapshot`;
- `commandRejected` — код и понятное описание ошибки;
- `pong`.

Событие содержит новую `revision`. Для простоты первая версия может рассылать полный `GameState` после каждого принятого изменения. Позже можно перейти на события и периодические снимки.

## 6. Доменные модели

```dart
@freezed
class GameState with _$GameState {
  const factory GameState({
    required String roomId,
    required int revision,
    required GamePhase phase,
    required List<Player> players,
    required String? activePlayerId,
    required BattleState? battle,
    required DateTime? turnEndsAt,
    required DateTime updatedAt,
  }) = _GameState;
}

@freezed
class Player with _$Player {
  const factory Player({
    required String id,
    required String name,
    required int level,
    required int strength,
    required bool isHost,
    required bool isConnected,
  }) = _Player;
}

@freezed
class BattleState with _$BattleState {
  const factory BattleState({
    required String id,
    required String playerId,
    required int playerPower,
    required int enemyPower,
    required BattleStatus status,
    required DateTime? endsAt,
  }) = _BattleState;
}
```

Реальные поля уточняются правилами настольной игры. Модели должны быть сериализуемыми, неизменяемыми и отделёнными от виджетов и транспортных DTO. Для миграций локальных данных задаётся `schemaVersion`.

## 7. Ревизии и согласованность

- Начальная `revision` равна 0.
- Хост последовательно обрабатывает входящие команды.
- Каждое принятое изменение увеличивает `revision` на 1.
- Клиент прикладывает `expectedRevision` к команде.
- При несовпадении хост отклоняет команду и отправляет свежий снимок.
- `messageId` уже обработанной команды не применяется повторно.
- Хост периодически сохраняет снимок, чтобы пережить перезапуск приложения.

Хосту полезна небольшая очередь команд, чтобы два почти одновременных действия не изменяли состояние параллельно.

## 8. Таймеры

В состоянии хранится не уменьшающийся счётчик, а абсолютное время `endsAt` в UTC. Каждый клиент отображает остаток как `endsAt - текущее время`, поэтому UI не требует сетевого сообщения каждую секунду. Хост определяет факт завершения таймера и публикует итоговое событие. При подключении можно оценить смещение часов с помощью `ping/pong`; критические решения всё равно принимает хост.

## 9. Виртуальный кубик

Клиент отправляет только `rollDice`. Результат генерирует хост, проверив право игрока на бросок. Хост публикует событие `diceRolled` с результатом, количеством граней, игроком, временем и новой ревизией. Клиенты лишь анимируют уже полученный результат. Это исключает расхождение результатов и простую подмену броска клиентом. Для настольного помощника достаточно `Random.secure()`; криптографически проверяемая честность потребует отдельной commit–reveal схемы.

## 10. Безопасность локальной комнаты

- Создавать случайный длинный `roomToken` с достаточной энтропией.
- Проверять токен при WebSocket handshake и не писать его в логи.
- Хранить токен в защищённом хранилище и удалять после закрытия комнаты.
- Привязывать команды к выданному `playerId`/сеансу и проверять роли.
- Ограничивать размер сообщений, частоту команд и число соединений.
- Валидировать JSON, типы, диапазоны и допустимые переходы состояния.
- Не доверять имени, времени, броску или вычисленному состоянию клиента.
- Закрывать комнату и сервер при завершении сессии.

Обычный `ws://` в доверенной домашней Wi‑Fi сети не шифрует трафик. Самоподписанный локальный TLS усложняет подключение. Для чувствительных данных следует использовать облачный режим с TLS; в локальном режиме нельзя передавать секретную персональную информацию.

## 11. Локальное хранение

Для настроек (имя, тема, последний адрес) подходит `shared_preferences`. Секреты хранятся в `flutter_secure_storage`. Снимок активной партии в минимальной версии можно хранить как JSON-файл атомарной записью; для истории партий и запросов позже использовать Drift или Isar, предварительно проверив актуальную поддержку целевых платформ.

Хост сохраняет состояние после принятого изменения либо с коротким debounce. В хранилище должны быть `schemaVersion`, `revision`, время сохранения и снимок. После аварийного запуска пользователь может восстановить комнату, но создаётся новый токен и клиентам требуется повторное подключение.

## 12. Ограничения платформ

### iOS и iPadOS

- Нужен текст разрешения Local Network в `Info.plist`; для Bonjour также перечисляются типы сервисов.
- Камере требуется `NSCameraUsageDescription`.
- iOS может приостанавливать приложение и сервер в фоне; стабильная работа предполагает, что хост открыт на экране.
- Симулятор не полностью заменяет проверку multicast, камеры и локальной сети на реальном устройстве.

### macOS

- В sandbox/entitlements нужно разрешить входящие и исходящие сетевые подключения; камере требуется отдельное разрешение.
- Системный firewall может запросить разрешение на входящие подключения.
- Для сборки, подписи и запуска macOS/iOS нужен Mac с Xcode.

### Android

- Нужны разрешения `INTERNET` и `ACCESS_NETWORK_STATE`; для получения Wi‑Fi-информации и mDNS могут понадобиться дополнительные разрешения, зависящие от версии Android.
- Камере требуется `CAMERA` и runtime-запрос.
- Multicast для mDNS может требовать `CHANGE_WIFI_MULTICAST_STATE` и multicast lock.
- Энергосбережение и переход в фон могут остановить сервер; в первой версии хост должен оставаться активным. Постоянный foreground service следует добавлять только при реальной необходимости.
- Android 9+ ограничивает cleartext-трафик; локальный `ws://` необходимо проверить и при необходимости явно разрешить только для локального сценария.

Устройства должны находиться в одной сети и видеть друг друга. Guest Wi‑Fi, VPN, client isolation, firewall и некоторые мобильные точки доступа могут блокировать соединение. При неудаче приложение должно показать адрес, порт и понятную диагностику.

## 14. Этапы разработки

1. Создать Flutter-проект, тему, навигацию и базовые модели.
2. Описать JSON-конверт, команды, события, сериализацию и версию протокола.
3. Реализовать чистую доменную функцию/сервис применения команд на authoritative host.
4. Создать `GameConnection` и тестовую in-memory реализацию.
5. Реализовать `HttpServer`/WebSocket-хост и локальный клиент.
6. Сделать создание комнаты, QR-код, сканирование и вход по имени.
7. Синхронизировать список игроков и полный снимок с `revision`.
8. Добавить ходы, `endsAt`, бой и виртуальный кубик на хосте.
9. Добавить переподключение, дедупликацию, восстановление и локальное хранение.
10. Настроить разрешения и протестировать реальные сети на всех платформах.
11. Добавить mDNS/Bonjour после стабилизации QR-сценария.
12. Позже реализовать `SupabaseGameConnection` как отдельный адаптер.

## 15. Тестирование

### Автоматические тесты

- Unit: правила игры, права ролей, переходы фаз, расчёты боя и таймеров.
- Protocol: сериализация/десериализация, неизвестные поля, неверные типы, совместимость `protocolVersion`.
- Host: валидация токена, revision conflict, дедупликация `messageId`, порядок одновременных команд.
- Integration: два и более клиента, разрыв связи, повторное подключение, запрос снимка, перезапуск хоста.
- Widget: создание комнаты, lobby, ошибки, таймер и результат кубика.
- Golden при необходимости: ключевые экраны на разных размерах.

В тестах часы и генератор случайных чисел внедряются как зависимости, чтобы проверять таймеры и броски детерминированно.

### Проверки на реальных устройствах

- Android ↔ Android, iOS ↔ iOS и смешанные пары;
- телефон-хост ↔ Mac-клиент и наоборот;
- домашний роутер, guest Wi‑Fi и мобильная точка доступа;
- выключение Wi‑Fi, смена IP, блокировка экрана, переход в фон;
- отказ в доступе к камере/локальной сети;
- QR с устаревшим адресом или токеном;
- несколько одновременных команд и подключений;
- большие/повреждённые сообщения и частые запросы.
